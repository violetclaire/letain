# Local Demo Data Plan

This is a planning document only. It does not provision data, run migrations, or
start product flows.

Local preview now has the app shell, Vite proxy, backend health, and committed
database migrations working against a disposable or staging database. The next
blocker is meaningful local Briarwood data. The existing `server/seed.ts` is
stale Beauvette sample data and must not be used for Briarwood preview.

## Goals

- Populate the smallest safe Briarwood operator demo in a disposable/staging DB.
- Make authenticated operator pages meaningful without changing auth behavior.
- Keep all outbound/external-effect surfaces inert.
- Keep the seed idempotent and removable.

## Non-Goals

- No production database writes.
- No schema changes or migrations.
- No email, SMS, payment, Square, contract send/signing, or public-token actions.
- No auth refactor and no Replit OIDC replacement.
- No use of `server/seed.ts`.
- No generated fake data that looks like a real person, real client, or real job.

## Auth Shape

Current local preview can use the existing email/password session path:

- `POST /api/auth/login` looks up `users.email`, verifies `users.password`, and
  sets `req.session.userId`.
- `/api/auth/user` returns the session user and includes `artistSlug` when an
  `artist_profiles` row exists.
- Replit OIDC remains available for current login/callback behavior, but local
  demo data should not require it.

Recommended demo path:

- Seed one deterministic local artist user with a bcrypt password.
- Seed an `artist_profiles` row for the same user with `artistSlug =
  "briarwood-demo"`.
- Use `/artist-login` and the seeded local email/password credentials.

The seed should never print or store a real password in logs. Use either a fixed
local-only demo password documented outside Git history, or require
`DEMO_OPERATOR_PASSWORD` in the process when the seed runs.

## Safety Gates for the Future Seed Command

The eventual seed command should refuse to run unless all gates pass:

1. `ALLOW_LOCAL_DEMO_SEED=true`.
2. `NODE_ENV !== "production"`.
3. `PUBLIC_BASE_URL` starts with `http://localhost:`.
4. `NEON_DATABASE_URL` or `DATABASE_URL` is present and parses.
5. The target DB host/name is not a known production host/name.
6. No production send/payment credentials are present:
   - `RESEND_API_KEY`
   - `TWILIO_ACCOUNT_SID`
   - `TWILIO_AUTH_TOKEN`
   - `TWILIO_PHONE_NUMBER`
   - `TWILIO_MESSAGING_SERVICE_SID`
   - `SQUARE_ACCESS_TOKEN`
   - `SQUARE_APPLICATION_ID`
   - `SQUARE_APPLICATION_SECRET`
7. `DEMO_OPERATOR_PASSWORD` is present, or the command explicitly prints a
   local-only generated password once to the terminal.
8. The command confirms `server/seed.ts` is not being run.
9. The command uses deterministic IDs and upserts, not blind inserts.
10. The command does not call HTTP routes. It writes rows directly through a
    reviewed script so no sends, webhooks, payments, or product actions fire.

## Proposed Future Commands

Implementation should be a separate PR. Suggested commands:

```powershell
# Seed or update the local demo data.
$env:ALLOW_LOCAL_DEMO_SEED = "true"
$env:DEMO_OPERATOR_PASSWORD = "<local-only-password>"
npx.cmd tsx scripts/seed-local-demo.ts
```

Optional cleanup command:

```powershell
# Remove only deterministic demo rows, in reverse dependency order.
$env:ALLOW_LOCAL_DEMO_SEED = "true"
$env:DEMO_SEED_ACTION = "cleanup"
npx.cmd tsx scripts/seed-local-demo.ts
```

The safest cleanup remains deleting and recreating the disposable Neon branch or
database.

## Idempotency and Cleanup Order

Seed should upsert by deterministic IDs. Cleanup, if implemented, should delete
only rows with known demo IDs and/or a shared metadata marker such as
`local_demo_seed = "briarwood-local-demo-v1"`.

Suggested cleanup order:

1. `inquiry_route_candidates`
2. `inquiry_internal_notes`
3. `inquiry_responses`
4. `inquiry_routes`
5. `schedule_drafts`
6. optional `contracts`
7. optional fake client `users`
8. `route_targets`
9. `inquiries`
10. `artist_profiles`
11. demo operator `users`

Do not cleanup by email domain alone. Only deterministic IDs or an explicit seed
marker should be trusted.

## Recommended Implementation PR

The next implementation PR should add a new script, not use `server/seed.ts`.

Likely files:

- `scripts/seed-local-demo.ts`
- `package.json` only if adding a script such as `seed:local-demo`
- docs update to this file with the exact approved command

The implementation PR must not start the server, call routes, run migrations,
send email/SMS, create payments, create Square links, send contracts, or touch
public-token behavior.
